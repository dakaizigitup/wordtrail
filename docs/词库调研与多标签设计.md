# 词库调研与多标签优先设计

调研日期：2026-10-05。阶段：来源与构建方案调研；尚未接入输入法，Android 仍为 0.1.7，Windows 补丁仍为 0.1.1。

## 已确认的需求

- 用户手动选择四级、六级、专四、专八、托福、雅思等学习目标，支持多选。
- 一个英文词允许有多个标签，例如同属四级、六级、托福和雅思。
- 中文候选顺序保留，只优先显示命中所选类别的英文译词。
- 非目标译词仍然保留；没有标签的词不伪造类别。
- 标签不能让候选框变高、留下空白，或拖慢快速打字。
- 后续可增加考研、GRE、BEC、计算机等类别；专四/专八属于考试目标，计算机等属于专业领域。

需要由开发阶段先找词表、整理和生成索引。普通用户使用时只需选目标，不需要自己在 GitHub 找词库或手动下载 CSV。最终若做可选词汇包下载，下载、版本及校验应由应用处理，打字时仍只查本地索引。

## 实际数据检查

研究缓存已下载固定提交的 ECDICT CSV、Qwerty 代表性 JSON，以及 KyleBing 六类正序 simple JSONL。研究原始文件与合并索引保留在被 Git 忽略的 `build/vocabulary-research/`，不作为生产词库分发。实际统计只归一化首尾空白和拼写大小写，没有把短语拆成单词。

| 类别 | ECDICT 带该标签的行数 | Qwerty 选定文件的去重词数 | KyleBing 正序 simple 的行数 / 去重词数 |
| --- | ---: | ---: | ---: |
| 四级 | 3,849 | 2,607 | 7,508 / 4,544 |
| 六级 | 5,407 | 2,345 | 5,651 / 3,991 |
| 专四 | 无此标签 | 4,025 | 4,620 / 4,340 |
| 专八 | 无此标签 | 12,197 | 12,881 / 12,410 |
| 托福 | 6,974 | 4,264 | 13,477 / 10,367 |
| 雅思 | 5,040 | 3,575 | 7,002 / 5,275 |

这张表反映具体数据文件，不是官方考试总词汇量。Qwerty 的文件分别为 `CET4_T.json`、`CET6_T.json`、`Level4luan_2_T.json`、`Level8luan_2_T.json`、`TOEFL_3_T.json`、`IELTS_3_T.json`。KyleBing 文件为 `full_line_jsonl/simple/正序/<类别>.jsonl`。

额外抽查 Qwerty：程序员词表 1,700 个去重条目；计算机专业词表 1,665 个；建筑 630 行、去重后 542 个。技术标识符、短语和普通英语不能因为同处一个文件就混为“高级英语单词”。

ECDICT 实际 CSV 共有 770,611 行，但所选四类考试的标签并集仅 10,578 个去重词。研究合并三项目及计算机/建筑样本后有 18,396 个去重条目，其中 11,024 个有多个标签；仅保留 `词条 + 标签位掩码` 的 UTF-8 TSV 为 **216,244 字节（约 211 KiB）**，不是必须新增几十 MB 的整套词典。

在固定上游的 `assets/glossary/glossary-en.tsv` 中进行词面精确匹配，研究并集命中 10,674 种译词，覆盖 42,383 / 232,213 行中文释义候选。许多现有译词是短语、专名或领域表达，没有考试标签是正常结果。**这只是上游 TSV 词面覆盖检查，不是正式安装包覆盖率或语义准确率**；不能因短语含有某个四级词，就把整条短语标为四级。

## 设置与候选展示

建议默认“全部词汇”：所有已有英文译词参与显示，保留原顺序。设置页提供多选项：四级、六级、专四、专八、托福、雅思；不选目标时不额外排序，选一个或多个时采用“任一命中即可优先”。

第一版不再加入复杂的标签权重或人工难度排序。命中者靠前，同组继续保留原译词顺序；非命中词保留在后面，不清空或替换为与中文无关的考试词。用户以后确实需要多个目标的先后顺序时，再增加明确的目标优先级。

例如，原译词序列为 `A、B、C`，选择雅思后若 `B` 命中，显示顺序变为 `B、A、C`，三个仍然都可查看。一个词的标签是集合，不是单个等级。CEFR 继续单独保留。

候选行最多显示两个小标签及 `+N`，选中类别优先显示；展开详情可看到该词全部标签、来源和音标。这样不会因六个标签把 46dp 候选行撑高。标签属于对应的英文译词，不属于中文候选，也不会改变中文候选的编号或排序。

## 数据与性能设计

离线构建：固定来源提交 → 解析单词 → 保守归一化 → 同词标签求并集 → 去重/一致性检查 → 生成精简索引及来源清单。释义与 IPA 仍由当前系统提供，第一版标签不需要复制源项目的例句、图片或发音音频。

可以用 `u16` 的每一位表示一个稳定类别，匹配只需 `word_tags & selected_tags != 0`。类别编号固定，停用类别不复用旧位；超过 16 个类别时迁移 `u32` 或分组掩码。运行时只加载一次精简表，以 HashMap 或排序表查询；切换目标只改偏好掩码和刷新当前状态，不重新读取 CSV、词库或模型。

只处理当前可见的最多 9 个中文候选及其英文释义。现有上游 `Translation::MAX_SENSES` 为 2，通常最多 18 次标签查找；完全无输入、非英语学习模式或没有译词时跳过。查询与序列化继续在现有后台队列，界面线程只显示已生成结果，不做网络请求或磁盘扫描。

### 已完成的主机原型测量

原型源码：[benchmark_vocabulary_tags.rs](../scripts/benchmark_vocabulary_tags.rs)；原始结果：[vocabulary-benchmark.json](research/vocabulary-benchmark.json)。本机 AMD Ryzen 7 H 255 / Windows，Rust 优化编译；18,396 个词，先初始化，再测每批 9 个候选 × 2 条译词，混合已知/未知及大小写输入，包含归一化、查询和稳定优先排序。每种方式 10,000 个测量批次，另有预热。

| 查询方式 | 一批 P50 | 一批 P95 | 一批 P99 |
| --- | ---: | ---: | ---: |
| 排序表二分查找 | 3.3 微秒 | 6.2 微秒 | 9.9 微秒 |
| HashMap | 1.8 微秒 | 3.8 微秒 | 6.4 微秒 |

初始化两种结构约 2.79 ms，不包含文件读取。三个行为检查验证：多目标任一命中、命中/未命中分组保持稳定、未选目标原序不变。这个结果说明精简标签索引有可行的速度余量，**不能直接当成手机输入响应时间**；未包含 Android JNI、候选排版、完整拼音查询或启动阶段。

接入后必须在 Android 和 Windows 比较开启/关闭标签的端到端延迟、P95、连续快速触屏与冷启动，不能只测 HashMap 就宣布输入法更快。初步工程目标是标签查询及优先排序批处理 P95 < 1 ms；是否达到以目标设备测量为准。

## 现有代码需要联动的地方

当前 `native/src/session.rs` 把译词拼成 annotation，音标来自第一条 sense，长按固定 `commit_translation(candidate, 0)`。因此不能只在 UI 重排字符串：否则用户看见 `B`，长按却输入 `A`，音标和熟悉度也可能不一致。

建议在共享状态生成时对可见候选的完整 sense 做稳定排序，然后把排序后的候选用于显示、音标、等级、学习记录与长按上屏。中文 Candidate 的顺序保持不变。JSON 增加结构化 `translation_senses`，每条带译文、词性、tags、CEFR 及稳定 sense 标识；保留旧字段以便分步迁移。

“全出”第一阶段指保留原先可用译词，不意味着把整个考试词书塞进每个中文候选。当前上游最多提供两条译义，如果后续要展示更多同义译词，还需扩展释义数据和详情区，先审核语义，再单独评估性能。

Windows 使用同一标签数据和稳定排序规则，但还需要设置持久化、候选渲染与 Ctrl + 数字上屏联动；不能只给 Android 加了标签就声称两端已实现。iOS 可同步结构设计，实际支持仍需 Mac 编译验证。

## 分步推进

1. 本次：调研六个项目，下载代表性数据，查重复、覆盖、来源和精简索引速度，记录用户确认的规则。
2. 下一步：确定第一批数据来源与版本，形成可重建的词条/多标签索引，补充短语、变体与类别差异校对。
3. 接入共享状态及手动多选设置，让展示、音标和译词上屏保持一致；先做四级、六级、托福、雅思，再按来源核对结果加入专四/专八。
4. 分别验证 Android 与 Windows 的响应时间、快速输入及覆盖升级，再发布新版本；现有 v0.1.7 Release 保持原样。
